Developer Guide

This page is a map of the code: it names the parts, shows how they fit together and states the conventions shared by all of them. The details (signatures, formulas, costs) live in the docstrings, collected in the Code Reference, and the code itself remains the authoritative documentation. A change of the design updates this page in the same commit. When in doubt, follow the nearest existing example.

Nouns and verbs

PsiTK builds on DFTK's plane-wave infrastructure (e.g. PlaneWaveBasis, FFTs, Hamiltonian, exchange operators) and borrows its pattern: nouns are plain structs that carry either data or configuration, rather than both; verbs are functions that take the data they need as arguments and the configuration as a dispatch argument.

nounrolelives in
OrbitalSpacedata: orbitals, energies, occupation on a basis; what orbital-space verbs and interfaces consume and producesrc/orbital_spaces.jl

target, e.g. DensitySpecificVirtualsphysics: which eigenvalue problem defines the virtual orbitalssrc/virtual_orbitals.jl
solver, e.g. LOBPCGnumerics: how an eigenvalue problem is solvedsrc/eigensolvers/

operator, e.g. LevelShiftedOperatornumerics: matrix-free wrapper of a DFTK operator, applied with mul!src/operators.jl
callback, e.g. ShowProgressoutput: reports the progress of long computationssrc/callbacks.jl

The verbs transform the two data nouns into each other:

verbtransformslives in

A typical workflow composes the verbs like this:

occ_space, _ = split_occupied_virtual(OrbitalSpace(scfres))              # DFTK enters here
dsv_space    = generate_orbitals(DensitySpecificVirtuals(n_orbitals=50), occ_space, ham)
active_space = canonicalize_orbitals(merge_spaces(occ_space, dsv_space), ham)
fitting      = compress_coulomb_vertex(compute_coulomb_vertex(active_space), CoulombGramian())
dump_cc4s_files(active_space, fitting)                                    # src/interfaces/

src/PsiTK.jl includes the files in dependency order and declares the exports next to the include of the file defining them. Every export needs a docstring (docs/make.jl builds with checkdocs = :exports).

Conventions

  • k-points: per-k-point data are Vectors over k-points, e.g. ψ[ik] is an $N_\text{pw} \times N$ matrix of orbital coefficients and eigenvalues[ik] a vector. Verbs loop over k-points; the Coulomb vertex and the interfaces are Γ-point only so far.
  • Vertex layout: the Coulomb vertex Γ has the shape (Nk, Nbra, Nk, Nket, NG), or (Nk, Nbra, Nk, Nket, NF) once compressed.
  • Orthonormality: an OrbitalSpace records whether its orbitals are orthonormal (is_orthonormal). Orbitals of a generalized eigenvalue problem, e.g. DensitySpecificVirtuals, are not; canonicalize_orbitals makes them orthonormal, and the interfaces require it.
  • Callbacks: long computations take a callback keyword, called with a NamedTuple after each step; callback=identity silences it. Step-wise loops pass (; step, total_steps), which ShowProgress turns into a progress bar.

Extension points

Extending the code usually means adding one noun and its methods of an extension point. The docstring of each extension point states its contract.

Virtual-orbital targets and eigensolvers

generate_orbitals splits physics from numerics, so that targets and solvers combine freely. Per k-point it

  1. takes the eigenvalue problem (; A, B, ε_offset) of the target from _eigenproblems. The operators are matrix-free wrappers of DFTK operators (LevelShiftedOperator, ProjectedShiftedOperator) that push the occupied space out of the low end of the spectrum;
  2. builds a stochastic guess X0 of _n_guess(solver, n) vectors orthogonal to the occupied space, where n is the number of requested orbitals;
  3. solves for the lowest n eigenpairs with _solve(A, B, X0, n, P, solver);
  4. returns an OrbitalSpace, orthonormal or not as given by _is_orthonormal.
  • A new target is a configuration struct with an n_orbitals field, added to the VirtualOrbitalTarget union, plus methods of _eigenproblems and _is_orthonormal in src/virtual_orbitals.jl.
  • A new eigensolver is a configuration struct plus a method of _solve (and optionally of _n_guess) in src/eigensolvers/.

Compression strategies

compress_coulomb_vertex delegates to _compress_coulomb_vertex and accumulates the transformations of repeated compressions in the DensityFitting. A new strategy is a configuration struct plus a method of _compress_coulomb_vertex in src/coulomb_vertex.jl.

Correlation-solver interfaces

A new interface is a file in src/interfaces/ consuming an OrbitalSpace and a DensityFitting, so that only that file knows the solver's file format. It checks its preconditions (e.g. orthonormal canonical orbitals) itself, see dump_cc4s_files.

Computational cost

A few functions dominate the runtime and memory of a calculation once there are a few hundred virtual orbitals. To keep their cost visible, every public function and every extension point (target, solver, compression strategy) whose time or memory grows faster than linearly with the system size, i.e. with the number of orbitals or plane waves (log factors from FFTs do not count), documents its cost in a # Cost section at the end of its docstring:

  • time: the leading terms in O-notation and the step they come from;
  • memory: the peak memory in complex numbers (16 bytes each).

A change of the scaling updates this section. Following the split between physics and numerics, a target documents the cost of one application of its operators, and a solver its cost in terms of operator applications. For example, for compute_coulomb_vertex:

# Cost
Those of [`compute_overlap_densities`](@ref), which the vertex overwrites in place:
- time: ``O(N_\text{bra} N_\text{ket} N_r \log N_r)``
- memory: ``N_\text{bra} N_\text{ket} N_G`` complex numbers for `Γ`

Counts use the following symbols. In code, the name is the symbol without the underscore of its subscript ($N_G$ ↔ NG); counts without a symbol are snakecase (`norbitals). Each# Cost` section states which of its arguments the symbols refer to.
